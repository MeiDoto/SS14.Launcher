# ⚡ Архитектурное решение (ADR) 0002: Политика Async-безопасности и обработки ошибок

- **Статус**: Принято (Accepted)
- **Дата**: 2026-09-02 (Обновлено: 2026-09-08)
- **Область**: Асинхронные шаблоны, перехват исключений, логирование Serilog, предупреждения компилятора

## 📋 Контекст и проблематика

Как настольное приложение с насыщенным сетевым и файловым вводом-выводом, **SS14.Launcher** выполняет десятки параллельных асинхронных операций: опрос серверов по протоколу HTTP, замеры задержки сокетами TCP, скачивание пакетов контента, парсинг zip-архивов и запись конфигурации в SQLite.

Ранее в кодовой базе существовали две ключевые угрозы надежности:
1. **Необработанные исключения в `async void` методах**: любое исключение в таком методе приводит к падению всего процесса без возможности перехвата через стандартный `try-catch`.
2. **«Голые» и пустые блоки `catch { }`**: скрывали отладочную информацию при сбоях сети, ошибках DNS или отказе прав файловой системы, делая поиск багов невозможным.
3. **Предупреждения CS4014 (unawaited Tasks)**: вызовы методов, возвращающих `Task`, без ожидания (`await`) и без оператора сброса (`_ =`) порождали неуправляемые фоновые задачи (unobserved tasks).

---

## 🎯 Принятые решения

### 1. Строгий запрет `async void` вне UI-обработчиков
- **Правило**: Все методы бизнес-логики, сервисов и ViewModels **обязаны** возвращать `Task` или `Task<T>`.
- **Исключение**: `async void` разрешен **исключительно** для прямых методов-обработчиков событий Avalonia UI, сигнатура которых строго требует `void` (например, обработчики нажатия кнопок `RoutedEventArgs`).
- Все не-UI фоновые методы (`LoginManager.Impl`, `HttpSelfTest.RunTests`) переписаны на возврат `Task` либо заключены в защитный `try/catch`.

### 2. Шаблон сброса фоновых задач (`_ = Task`) и устранение CS4014
- При намеренном запуске фоновой задачи без блокировки текущего потока (fire-and-forget) разработчик обязан явно указать оператор сброса:
  ```csharp
  // ПРАВИЛЬНО: Намерение явно зафиксировано, CS4014 подавлен
  _ = _dataManager.CommitConfig();
  _ = RefreshServerListAsync(cancellationToken);
  ```
- В проект включена строгая проверка компилятора: предупреждение **CS4014** не допускается в кодовой базе.

### 3. Полный отказ от пустых блоков `catch` и структурированное логирование
- Пустые блоки `catch { }` и бестиповые `catch` **полностью запрещены**.
- Любое пойманное исключение должно быть типизировано `(Exception ex)` и залогировано через библиотеку **Serilog**:
  - `Log.Debug(ex, "...")` — для ожидаемых или некритичных сетевых сбоев (таймаут пинга отдельного сервера, недоступность опционального икон-хаба).
  - `Log.Warning(ex, "...")` — для нештатных ситуаций, не приводящих к фатальному сбою (ошибка обновления одного из зеркал CDN).
  - `Log.Error(ex, "...")` — для ошибок, нарушающих функциональность (невозможность подключения к базе данных, ошибка запуска процесса).
- Если переменная исключения не требуется для форматирования сообщения в безопасной ветке отката, используется `catch (Exception)` без объявления локальной переменной (для предотвращения CS0168).

### 4. Глобальные предохранители исключений
В `Program.cs` развернуты многоуровневые глобальные фильтры:
- `AppDomain.CurrentDomain.UnhandledException`: аварийный сброс журнала через `Log.CloseAndFlush()`.
- `TaskScheduler.UnobservedTaskException`: интеллектуальный фильтр, отделяющий безвредные сбои сокетов (таймауты DNS, отмена CancellationToken) от реальных системных сбоев с вызовом `SetObserved()`.

---

## ⚖️ Последствия и результаты

- **Результаты**:
  - **0 предупреждений CS4014** и **0 предупреждений CS0168** в релизной сборке.
  - Полное отсутствие падений лаунчера из-за фоновых сетевых таймаутов.
  - Диагностические логи содержат исчерпывающий контекст ошибок для локализации проблем игроками и администраторами серверов.
